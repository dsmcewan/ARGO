Runtime facts: `MECHANICS/tempted-fates-v1.md:9,15,22,34–36`, `packages/ledger/src/mechanics.ts:21–36,64–85,90–123`, `packages/ledger/src/index.ts:74–119`, `packages/lexi-bridge/src/index.ts:23–43`, and `packages/interventions/src/index.ts:7–17` establish:

- One v1 tick is one second. Only authorized `advance_time` increases it; advancing the clock does not automatically age actors or debit lifespan. Ordinary proposals use the current world time and exact head/sequence.
- A private global RNG index advances only for accepted `draw` events. The current algorithm is `hmac-sha256-u32-rejection-v1`; replay validates hidden draws and blinded commitments. Rejection and narration consume none.
- Acquisition time is observation commit time. Actor and party views require explicit observers, acquisition-time and sequence cutoffs, and current anomaly policy. Membership does not union private knowledge.
- `serialize`/`reject` are supported; queue/fork are refused. Exact proposal retries bind the original proposal bytes and principal and return the prior outcome. Cancellation after submission can race append; it does not prove rollback.

## D06 draft: clock, expedition, and delivery semantics

**Proposed first supported mode:** an explicit authority-driven world clock; appointments and host timers never drive it. A session pins full immutable scope, participants, head, sequence, world time and expiry. An expedition ID is a coordination identity, not a world branch or permission to write behind the head. Initial fixtures use fixed genesis party membership. Dynamic membership, retroactive expeditions, queue/fork return and automatic catch-up remain outside this draft.

At contention, the writer accepts an ordered commit and rejects stale proposals. Do not promise that the same network race has the same winner: a deterministic fixture controls the arrival/lock barriers. Replay determinism applies to the recorded accepted order. A loser must obtain a fresh authorized view and make a new decision; the coordinator cannot silently rewrite its checkpoint or proposal ID.

**Proposed delivery meaning:** distinguish `prepared`, `released`, `recipient_acknowledged`, `observation_committed`, and `reconciled/failed` transport states. A recipient acknowledgement means the recipient endpoint accepted the specified payload, not proof a human understood it. Narration generation and a send attempt alone never create knowledge or donor consent. Recheck scope, recipient rights and current presentation cutoffs before releasing content. Bind acknowledgement to scope, recipient, delivery ID and exact payload digest. Recheck at observation commit. If authority/presentation policy changed, fail closed and record the unresolved delivery state rather than backdating acquisition.

A subsequent authorized observation uses a stable proposal/claim identity; retries cannot append duplicate knowledge. `acquired_at` remains commit time even when the source occurrence is older. A lost acknowledgement leaves delivery uncertain; reconcile the same identity rather than minting a fresh successful observation. Late stale proposals are rejected and require a new explicit current-time decision. The precise release/authorization race and acknowledgement recovery protocol must be reviewed before production: once content was actually released, a later rejection cannot make it unseen.

New transport metadata may include `delivery_id`, `payload_digest`, recipient, source claim/event reference, release-policy checkpoint and acknowledgement identity. These are proposed fields; v1 `Observation` must not receive invented properties. Rumor transmission may become a new observation, but canonical truth, source content, authority-only assessment and acquisition are separate. Time-dependent truth classifications must not leak through narrator text or ranking. Current anomaly cutoffs continue to constrain historical queries.

## D10 draft: bounded tick oracle, not production constants

Use an isolated fixture policy `hd-tick-fixture/1` with explicit finite values: starting world time100 seconds, authorized target104, one second per logical step, at most2 ticks per invocation, exactly2 registered entities (`a`, `b`), at most1 active project per entity, at most2 evaluated candidates per tick and at most4 proposed effects. These values make small boundary tests legible; they are not throughput evidence, defaults or recommended deployment capacity. Test M−1/M/M+1 boundaries and safe-integer overflow. Reject an oversized configuration or tick atomically; never silently omit entities to meet a cap.

The pure fixture rule is: in canonical entity-ID order, an entity with an eligible unfinished project and at least1 resource proposes spending1 resource for1 progress; otherwise it waits. A completion can create one follow-up eligible no earlier than the next tick. It cannot recursively execute that follow-up. This invented fixture rule is an ARGO test hypothesis, not a Knave/Blades/SWN quotation or an implemented v1 action. Example: resource1, progress3/4 at100 yields resource0 and one completion at101; any follow-up must wait and cannot manufacture another resource. Track spent resources explicitly so initial stock equals remaining plus spent.

One logical tick is staged from one immutable checkpoint; authority validates all effects, principal capabilities and bounds under the writer lock, then accepts the entire tick and durable cursor or accepts none. Crash recovery must not advertise a cursor ahead of committed effects. The proposed atomic multi-effect tick and durable catch-up cursor require a dedicated versioned action/state contract; existing `advance_time` alone does not implement them. Pending work beyond an invocation budget remains explicit authorized backlog. No ambient wall time, sleep duration, container restart or narrator action authorizes more ticks.

**RNG proposal:** if a later scheduler needs batching-independent random slots, bind them to versioned scope/ruleset/policy, logical tick, stable entity/project identity, named slot and distribution/bound parameters; exclude HTTP attempts, batch size, arrival timing and model retry IDs. Keep the seed and unrevealed draws authority-private. This differs from the v1 global-index algorithm and is a migration proposal. Existing projection fixtures should use the current v1 `draw` contract unchanged. Compare state and slot commitments across 2+2 versus1+1+1+1 runs; demand identical full event hashes only when genesis/key, proposal/envelope identities and accepted ordering are also fixed.

**LLM boundary:** determinism covers scheduling, validation, adjudication and replay of exact recorded inputs. It does not promise identical model-generated plans from a seed or temperature setting. For any later stochastic planner, retain the exact selected proposal bytes, input-view/checkpoint digest, planner policy/version and acceptance identity in authority-appropriate provenance. Replay consumes the accepted recorded proposal/event and never calls the model again. Different proposals may yield different valid outcomes. Unaccepted suggestions remain noncanonical; neither their generation nor retry consumes gameplay randomness or grants consent. For the initial tick oracle, planning is a pure finite table and no model is invoked.
