# Offline Mesh integration: acceptance and trust audit

Read-only source review at ARGO `140b644c0bb86f45141f23b7f00788aeae04e389`. No implementation, tests, vendor calls or repository changes were performed in this review. The supplied TELOS #205 source head is `acc61c2abcf3611d2b3f7c7b03d59d493316f292`; this contributor did not independently retrieve that source. Record the actual imported/adapted file identities during implementation rather than treating the moving PR number as provenance.

The deliverable should be an executable, bounded offline dispatcher/adapter that starts multiple real confined builds, produces separate candidates and traces, and supports their independently verified serialized integration. A design packet, mocked scheduling overlap or Pantheon `shipped:true` alone does not satisfy that goal. Offline native workers and injected Pantheon clients are sufficient; no provider credentials or paid runs are needed.

## Existing boundaries to preserve

- `tools/dispatch.py:530` currently awaits `_one` inside a finite `max_tickets` loop. It is sequential, despite the lifecycle using async I/O. `_one` already provides lease renewal/expiry, fresh detached worktrees, bounded Bubblewrap workers, immutable-base Git commits, owned artifact collection and fenced submission. Reuse this lifecycle instead of creating a second writer protocol.
- `tools/board.py:470` claims through a SQLite transaction and excludes overlapping paths held in CLAIMED, VERIFYING, REVIEW or MERGING. A new epoch has a fresh token and worktree. Heartbeat, artifact publication and submission recheck ownership/expiry. Existing cross-process claim tests establish one winner for one ticket, not successful parallel builds end to end.
- Worktree and lease ownership is scoped to one Board database. The merge `flock` is under that board directory (`tools/board.py:785`). Two boards pointed at the same repository do not share path locks or that merge lock. Use one authoritative Board per shared target in the first implementation, or add and test an explicitly shared lock/ownership domain; do not advertise cross-board exclusion without it.
- `Dispatcher` workers see the worktree read-only except declared writable paths, a bounded input directory and temporary storage. They cannot see Git control metadata, the board database, supervisor capabilities, host credentials or network. Exact-file mounts do not grant atomic rename/delete; directory ownership does. Preserve those semantics and alias checks under concurrency.
- `run_bounded` owns a process group and bounds output, execution and pipe lifetime; lease loss stops it. No cgroup CPU/RAM/PID/disk quotas are currently supplied. A concurrency setting is a scheduler capacity limit, not a host resource-isolation guarantee.
- Pantheon's `runOrchestration` concurrently invokes seats and combines outside-model verdicts. `runOpenItem` has its own refs/CAS, copied worktree, output tree and shipping state. These are distinct from Python Board leases/Git acceptance. It also has default home-based storage and provider-routing paths: the offline adapter must inject clients, roots and cooldown storage explicitly and must not accidentally reach a real CLI/SDK fallback.
- Board v1's pinned Python data gate cannot import candidate Python, execute Node/npm or spawn the application controller. `controller/merge.mjs` is the existing external application acceptance path, with complete trusted tests/policy, exact Git tree extraction, isolated checks and safe fast-forward. Its current target-head recheck is not a repository-wide scheduler lock. Serialize its invocation through one trusted merge owner; do not run competing controller processes against main.

## Minimal useful implementation scope

1. Add an explicit bounded concurrency setting independent of total claim/attempt budget. Reserve a local capacity slot before claiming; do not acquire an entire queue of leases that expire while waiting. Retain dry-run as side-effect-free and offline execution as explicit. Reject invalid limits before claims or process launch. State whether capacity is per dispatcher or shared across dispatchers; a global limit requires durable shared accounting, not an in-memory semaphore.
2. Mesh is the trusted supervisor's scheduler/transport adapter; Python Board remains the authoritative ticket/lease/CAS state machine. No worker-selected board paths, lease tokens, trusted-policy SHAs, arbitrary supervisor methods or merge commands. A proposed child task remains data until the supervisor admits a later immutable batch. Do not silently introduce a dynamic DAG.
3. Give each execution a supervisor-created build/run ID bound to repository, board instance, ticket, epoch, base SHA, spec/policy identity and unique worktree/runtime/output roots. Keep a distinct bounded stdout/stderr/progress trace and terminal record for each attempt. Do not place capabilities in worker-visible manifests or logs. Distinguish requested model labels from injected offline execution; `mesh complete`, model text and Pantheon shipping are never gate receipts.
4. Run actual worker children concurrently with isolated environments. A failed build must not lose successful siblings' results or cancel them accidentally. Choose and document fail-independent versus fail-fast policy; fail-independent is the simplest useful default. Stop claiming on cancellation, cancel and reap owned children, then settle every claimed attempt without inventing completion. A shutdown cannot steal a newer attempt's lease to record the old failure.
5. Keep build submission and acceptance separate. The first version may emit VERIFYING candidates and drive the already authorized supervisor verification/controller workflow; it must not claim general D09 application-ticket acceptance inside Board v1. For an automated data-fixture smoke test, existing Board verify/review/merge can prove real Git/CAS integration. Real ARGO application candidates still require the separately trusted full application controller before main.
6. Handle sibling-base staleness deliberately. If A and B build from base H, after A integrates the board refuses B with TARGET_STALE and returns it for a fresh attempt. Reapply/rebase its owned delta under a new lease/base and rerun the exact candidate gate; do not reuse the old verdict or blindly cherry-pick into main. For a minimal demonstrator, rerunning B's deterministic fixture from the new base is acceptable if the superseded attempt and bounded retry are explicit. Durable MERGING intent remains supervisor recovery work, never a worker retry.

## Required executable acceptance cases

All cases below are proposed and **not executed by this review**. Reuse real temporary Git repositories, Board SQLite and native Bubblewrap where the invariant concerns them; do not replace the board/runner with stubs in the integration oracle.

| Case | Observable acceptance |
| --- | --- |
| Two builds overlap | Two independent tickets reach a supervisor-observed running barrier before either is released; distinct child PIDs and detached worktrees; both produce their owned edits and immutable candidates. A sequential dispatcher must fail the bounded barrier. Avoid proving overlap solely from elapsed wall time. |
| Capacity and finite budget | With capacity two and at least three ready tickets, at most two workers run; no third lease is preclaimed before a slot opens; finite attempt budget is honored. Verify advertised multi-process capacity semantics separately. |
| Independent processes | Start two dispatcher OS processes against one real Board; disjoint tickets can both run, while the same ticket and ancestor/descendant owned paths have only one owner. Same-name unrelated paths remain eligible. |
| Lease fencing/restart | Kill or stall one supervisor, expire/reclaim its lease, then deliver its late heartbeat/output/submit. Old attempt is refused; new epoch gets another worktree; no old artifact becomes accepted. A delayed heartbeat cannot keep its old worker alive indefinitely. |
| Isolation | A tries writing B's path, reading B's trace, board SQLite, host Git config or credential sentinel, and using network. All are unavailable/refused; B still completes. Test exact-file versus directory write semantics and symlink/hardlink aliases. |
| Trace separation | Same human build label in two attempts still yields distinct run/trace roots. Interleave progress and stdout with distinct sentinels; each record maps to exactly its own ticket/epoch/base. Oversized output is bounded and terminal failure retained without truncating another build's trace. |
| Timeout and cancellation | One worker ignores SIGTERM and spawns a descendant holding stdout; timeout/cancel kills its owned group, closes pipes, settles the attempt within bounds and leaves an unrelated worker alive. Cancellation before claim launches nothing; cancellation during collection/publication cannot submit after lease loss. |
| Crash/partial publication | Stop after commit creation or one CAS upload but before submit. Restart does not double-submit or mark accepted; orphan bytes do not become dependency input. Only accepted predecessor artifacts unlock dependent work. |
| Fake success/refusal | Worker prints success, supplies another build's SHA or emits an application-looking receipt. It cannot set REVIEW/MERGED, choose trusted policy or pass a data/application gate. A zero exit with invalid output fails. |
| Exact candidate and policy | Unowned/pinned changes, mismatched CAS bytes, altered candidate tree, changed trusted test and missing normal completion all refuse. Independently reviewed new test inventory must be promoted before controller acceptance. |
| Concurrent build, serial merge | Hold two completed siblings at H; integrate A; B's old candidate is refused as stale. Fresh B attempt on A's head is verified and integrated; final tree contains both changes, each accepted CAS reference belongs to the successful epoch, and Git/audit history records the actual order. |
| Competing integration owners | Two attempted mergers for the supported shared target cannot concurrently mutate its ref/index/worktree. If different board directories are unsupported, refuse that configuration before dispatch rather than relying on per-board locks. |
| Integration recovery | Interrupt after ref update but before acceptance, and again during recovery. Existing durable intent, retained path locks, exact re-verification and one accepted handoff survive; no duplicate accepted artifact or fabricated MERGED state. |
| Offline Pantheon/Mesh route | Run the real adapter with injected deterministic clients and explicit temporary stores. Verify route/task/result correlation, reject duplicate/misbound completion, and prove no real vendor constructor/CLI, credential lookup or network fallback is reached. No mocked success-only transport can replace the native overlap case. |

## Policy promotion and completion evidence

Changes under `tools/` alter the controller's fully pinned Python control plane. Changes under `controller/`, `scripts/`, `TESTS/`, `pantheon/tests/` and dependency manifests also alter protected policy. Independently review those exact bytes before creating the new trusted checkout and binding its immutable SHA outside candidate control. If executable/policy identities pinned by an active Board change, stop old supervisors and initialize a newly reviewed board; do not rewrite a live ticket to accept the repair. Keep frozen gameplay v1 files unchanged.

Use conventional named unittest methods/top-level Node tests supported by the existing parent runners. Run focused new concurrency and adapter cases first, then the affected existing suites and complete ten-group application gate once on the exact final candidate. The final evidence should retain source head/file provenance, reviewed policy hashes, candidate/trusted/base SHAs, real per-attempt trace manifests, overlap barrier observations, SQLite/audit states, candidate/CAS identities, native namespace result, cancellation/timeout outcomes and final target HEAD/tree. Clearly label any remaining unsupported cross-board or resource-capacity behavior. Existing design cases and unit mocks must not be reported as newly executed native concurrency proof.
