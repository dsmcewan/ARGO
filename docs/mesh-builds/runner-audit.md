# ARGO bounded concurrent runner audit

Read-only source audit at `/workspace/ARGO`, HEAD `140b644c0bb86f45141f23b7f00788aeae04e389`. No repository changes, worker execution, dependency installation, paid calls, or recursive agents. TELOS PR #205 itself was not supplied to this lane; this report describes ARGO integration requirements and does not certify that PR's wire format or implementation. The already-running projection controller is a separate operation; do not alter its policy or board in flight.

## Recommended scope

Add bounded ticket concurrency to the trusted ARGO supervisor, using the existing SQLite Board as the sole ARGO scheduling/lease authority. A Mesh-facing adapter should submit/status/cancel *build jobs*, map their immutable identities to Board tickets/attempts, and expose evidence. It must not become a second owner of ARGO leases, a source of authoritative acceptance, or an alternative merge mechanism. Keep the first proof entirely offline with injected fixture runners. Live provider execution remains disabled.

The minimal useful change is `Config.max_concurrent`, a bounded active-task scheduler in `Dispatcher.run`, per-attempt cancellation and terminal records, plus offline real-Board multi-worker tests. Default concurrency remains one, default `max_tickets` remains one, and `--once` continues to prohibit multiple tickets. An explicit local fixture run can request `--offline --max-concurrent 2 --max-tickets 4 --command-json '[...]' --seat-model <registered-label>`. A scheduling label does not assert that a model executed.

The broader Pantheon bridge needs a separate adapter contract and fixes below before it is advertised as an ARGO worker backend. `runOpenItem` is a full build/review/ship pipeline, not a drop-in worker command. Wrapping it directly would also collide with ARGO's intentionally networkless/credentialless Bubblewrap worker environment. A future host-side provider broker must remain outside that sandbox, expose only bounded generation/artifact operations to a worker, and leave ARGO verification/review/integration with the supervisor. Mock that boundary now rather than granting workers host network, credentials, board DB access, or merge commands.

## Concrete scheduler design

1. Keep `Board.claim` authoritative. A supervisor acquires a bounded execution slot **before** claiming; do not reserve dozens of leases while their workers sit queued. Use a small reviewed cap, e.g. 1–8 concurrent attempts. The existing maximum 100 total tickets remains a separate bound. Do not claim every READY row and merely semaphore the child launch.
2. `Dispatcher.run` maintains active tasks and monotonically counts claimed attempts. Fill free slots, await `asyncio.wait(..., FIRST_COMPLETED)`, collect terminal results, then refill while total budget remains. A returned `None` means no eligible work at that moment; if active work exists, drain it and permit a bounded recheck. If none is active, return a finite idle result. A descendant will not become ready merely because its parent submitted: ARGO dependencies require MERGED, and dispatch must not secretly verify/merge to unlock them.
3. Each child gets its immutable `(board identity, ticket_id, epoch, worker_id, lease_token, base_commit)` and an independent cancellation event. Mesh-visible job IDs/status must exclude the secret lease token. Derive distinct worker/slot IDs within Board's 100-character grammar; include ticket+epoch on logs. A Config object must not be mutated while sibling `_one` calls read it.
4. On one ordinary worker failure, record its result and keep independent siblings running. On explicit supervisor cancellation, cancel all active children, await bounded cleanup, and attempt fenced `fail_claim` for each; never return while an owned child or publication task remains live. A global infrastructure failure should stop admitting new work and drain/cancel according to an explicit documented policy. Preserve SIGINT behavior and add a tested SIGTERM path; an OS default SIGTERM is not equivalent to asyncio cancellation.
5. Report results in a stable order (claim ordinal or ticket/epoch), not nondeterministic completion order. Include start/end/attempt/candidate/artifact identities and per-job failure, plus active/queued counts and total admission count. None of these fields is a gate pass or review approval.
6. Define cap scope honestly. `max_concurrent=2` in one process does not prevent a second dispatcher from launching two more. For an initial single-supervisor Mesh service, hold an OS advisory supervisor/admission lock for that board and make duplicate startup refuse. If multiple Mesh supervisor processes are required, add transactional durable slot admission to Board instead; do not derive a global cap from occupancy JSON. OS host capacity quotas remain separate.
7. `asyncio.to_thread` calls do not stop their underlying thread when cancelled. Board methods therefore still need fencing at their write point; retain those checks. Do not let a saturated shared executor queue heartbeats behind long worktree/Git operations. `claim` and `prepare_worktree` currently execute Git inside write transactions (`tools/board.py:491,511`); `_connect` permits a 10-second SQLite wait, while short leases may be only three seconds. Real contention tests must show timely fail-closed cancellation. If reducing transaction duration becomes necessary, separately design a durable reservation/create/finalize protocol; moving Git outside transactions without fencing is not a safe shortcut.

## Shared files and Pantheon lifecycle gaps

These are source-confirmed risks for the proposed integration; no live-provider reproduction was run.

* **Run directories/output aliases:** `runOpenItem` derives `root` from `open-${spec.key}-${Date.now()}` (`:133`) and writes `REPO_ROOT/outputs/open-items/<key>` (`:137`), including `run.json` (`:178–184`), shared progress JSONL (`:200–204`), prompts, and artifact exports. Different explicit roots still collide for the same key. The build-server Set is process-local and direct callers bypass it. Use UUID/epoch-qualified run directories and output roots; a display-only `latest` pointer may be atomically updated after completion. Lock same-attempt resume; the check for an existing `run.json` (`:376`) is not a cross-process mutex.
* **Occupancy is not admission:** `openRuntime.setOccupancy` (`runtime.mjs:138–142`) performs an unlocked read/modify/write of the whole JSON object. Two processes can each read the old map then overwrite the other's seat entry despite atomic rename. Keep it display-only, or update under a cross-process lock. `writeJson` uses a PID suffix (`:26`); current synchronous writes avoid same-event-loop interleaving but are not a general async update primitive.
* **Budget is observation, not reservation:** `setBudget`, `recordSpend`, and `budget` (`runtime.mjs:146–163`) write a declaration and append/read spend. Parallel jobs can both see capacity then spend it; no in-flight reservation exists. If paid execution is ever enabled, admission must reserve per-pool/token/cost budget transactionally before calls and reconcile afterward. Keep the provider-scoped shared cooldown store shared; do not isolate rate-limit state per build just to obtain overlap. No paid execution is authorized here.
* **Lease expiry does not stop Pantheon work:** slot leases are acquired once for 30 minutes (`run-item.mjs:569–574`); `runOpenItem` does not renew/watch them. Runtime `renew` (`runtime.mjs:104–109`) does not itself reject expiry if the generation has not changed. Ref publication still rejects expired leases, but that only fences publication; it does not terminate work at lease loss. ARGO's outer lease must own cancellation, and any reused Pantheon leases need a heartbeat/expiry lifecycle before they can promise that behavior.
* **Failure returns before siblings finish:** the slot `Promise.all` (`run-item.mjs:584`) rejects on the first failed slot; successful pending callbacks can later write artifacts and update `run.files`/`run.json` (`:625–637`) after the catch returns a failed run (`:797–810`). Use linked cancellation plus settle/drain of every slot before emitting a terminal run record or releasing admission. A sibling failure must not leave hidden activity after the build server deletes its key from `running`.
* **Cancellation stops short:** regular SDK routing receives `opts.signal` (`run-item.mjs:337–339`), but `runAcceptance` calls `isolatedAcceptance` without one (`:351–352`), and `acceptance.mjs:8,25` neither accepts nor forwards a signal even though `spawnPromise` supports it. `agyTurn` also has no signal parameter (`run-item.mjs:213`), and AGY subprocess calls omit it (`:250–262`). `createBuildServer` has no job AbortController/cancel endpoint and does not pass a signal (`:187`). Thread a linked job signal through every call, sleep/lock wait, acceptance child and AGY child; process-group termination must be observed before completion. Server shutdown requires explicit draining/cancellation; a disconnected SSE client need not automatically cancel a paid build.
* **A transport lock can silently serialize slots:** `sdkTurn` locks `seatKey(vendor,purpose,cwd)` (`pantheon/src/sdk/seat-sdk.mjs:65–86`) unless explicit scope/session identity refines purpose. `runOpenItem.turn` uses purpose `${purpose}@${pool}@${model}` with the same worktree/home (`:313`); same-model work slots therefore target the same conversational seat and lock. A Promise.all fanout is not proof of actual model concurrency. A future adapter must include slot+attempt identity in session/scope while preserving per-session serialization and shared per-pool cooldown. Prove overlap with injected delayed clients.
* **Status rendering is advisory:** `Board.render` reads under a transaction then atomically replaces `.board/BOARD.md` afterward (`board.py:888–898`). Concurrent renders may publish an older snapshot last. This is acceptable only as a display; scheduling reads SQLite, never Markdown.

## Verification and integration remain separate

`tools/README.md` specifies that Board v1 accepts pinned Python standard-library **data validators**. `Board.verify` is not a license to run npm, Node application tests, arbitrary pytest imports, or a Pantheon command inside that trusted validator process. Worker-produced `ok`, `shipped`, Mesh status, Pantheon repro metadata, and exit zero cannot set ARGO REVIEW/MERGED or bypass the independently owned gate.

For full application candidates, preserve the independently pinned `controller/merge.mjs` boundary: exact candidate/trusted SHAs, exact archived Git tree, protected policy, confined full gate, and clean target checks. A future Board-to-application-controller receipt adapter needs explicit exact-candidate/trusted-policy binding; it is a separate reviewed gate feature, not a generic gate-command substitution.

`Board._merge_lock` (`tools/board.py:784`) serializes **Board** merge/recovery. `Board.merge` (`:794`) requires passed gate/review, clean target, exact base, durable MERGING intent, and expected-old-value ref CAS (`:826`). Sibling A and B built from the same base do not both fast-forward: after A integrates, B's base is stale and `_retry(... TARGET_STALE ...)` (`:806–807`) requires a new attempt/candidate/test. Do not reuse B's old acceptance after a rebase/cherry-pick. An optimized patch-replay lane must create a fresh immutable candidate and independently rerun the full required gate/review.

`controller/merge.mjs` does **not** acquire `Board._merge_lock`; its own clean/head checks are not a cross-supervisor integration mutex. Mesh must have one trusted repository integration queue covering both pathways, or add a reviewed shared OS lock observed by both. Builds can run concurrently; target-ref/worktree integration and recovery serialize. Do not launch a competing integration while the existing projection controller is active.

## Tests and offline acceptance for the future ticket

Existing suites worth retaining: `tools/test_dispatch.py` (dry-run, bounded claim errors, CAS input verification, ownership, heartbeat expiry, descendant termination), `tools/test_board.py` (cross-process atomic claims, path conflicts, stale leases, exact owned/artifact submission, target staleness/ref CAS, interrupted merge recovery), and `tools/test_board_dispatch.py` (real Board/Git/Bubblewrap parent handoff and data-gate rejection). Pantheon already has `tests/view-build-server.test.mjs` (two builds overlap, third/duplicate refusal, event identity), `tests/board-multi-slot.test.mjs`, `tests/board-lock-domain.test.mjs`, `tests/board-fencing.test.mjs`, and `tests/acceptance-sandbox.test.mjs`. These were inspected by source; not rerun in this audit.

New independent tests should prove:

1. Two disjoint fixture workers actually overlap using an interprocess barrier, while maximum observed live workers never exceeds the requested bound; default dry-run still creates zero claims/processes.
2. Total claimed attempts never exceed `max_tickets`, including failure/retry; conflicting paths/dependent children do not enter workers early; no eager queued leases expire before launch.
3. Per-job cancellation, supervisor SIGINT/SIGTERM, blocked heartbeat and expired lease stop the entire affected process group before a terminal event. An unrelated sibling continues on local failure; global cancellation drains every sibling. No artifact/submission lands after fencing.
4. Concurrent attempt roots, specs, input CAS refs, SDK session identity and output manifests remain distinct. Same ticket/epoch resume from two processes refuses. Same-model injected slot calls overlap only when separate session identities are intended.
5. A failing Pantheon slot cannot leave writes/progress/acceptance after terminal failure; cancellation reaches SDK, AGY and acceptance subprocess seams without live calls.
6. Two independent supervisor processes obey the chosen admission scope; occupancy lost updates and double budget reservation are either prevented or explicitly excluded from authoritative decisions.
7. Concurrent candidates never advance the target before independent gates; first merge makes the sibling stale; stale evidence cannot authorize its rebased candidate. Board data-gate results and Pantheon/Mesh success flags cannot impersonate the full application controller.
8. No runner can edit protected tests/policy and then self-certify. New scheduler/adapter tests and control-plane files are included in the controller's protected acceptance policy review before freeze.

Run Python suites with `python3 -m unittest discover -s tools -p 'test_*.py' -v`; use Pantheon's existing parent-owned named-assertion runner for targeted Node test files and the repository full gate after integration. Native subprocess/Bubblewrap checks may require the execution environment's permitted escalation; sandbox-suppressed child output is not a valid green test result. No live API probe is needed for any of the acceptance above. CPU/RAM/PID/disk quotas and durable remote Mesh authentication are not supplied by concurrency counts, and remain separate design requirements if production deployment enters scope.

## Follow-up: smallest actual three-peer Mesh loop

The supervisor's proposed CLI spelling `--parallel 3` is reasonable for the same bounded `max_concurrent` behavior above; it must remain distinct from **three peers per attempt**. Three simultaneous authors each with three simultaneous peers can launch nine peer children at once. Bound total child admission as well as author-attempt admission, or clearly configure independent author/peer pools with a small fixed aggregate ceiling. Heartbeat/watchdog tasks must never consume a child-capacity slot.

Recommended first Mesh behavior: one author writes a candidate; three explicit offline peer commands inspect it read-only in **two barrier-separated rounds**. Round one independently identifies bounded, cited findings. Each round-two peer receives the same candidate and the complete bounded round-one transcript, then confirms, withdraws, or challenges findings. This is a real peer interaction loop rather than three unrelated reviews. A deterministic host reducer preserves disagreements and failures and emits one final trace. No model or script declaring `approved` creates a Board gate pass, external reviewer identity, or merge authorization. Registered seat/model labels are scheduling metadata only; three local commands are not proof of three independent vendors.

### Exact lifecycle seam

Add an optional trusted callback/protocol to `Dispatcher.__init__`, e.g. `pre_submit`, invoked by `_one` after `commit = await self._commit(...)` and before `put_artifact`/`submit` (`tools/dispatch.py:500–509`). The hook receives only a supervisor-constructed request `{ticket_id, epoch, base_commit, candidate_commit, spec_sha256, upstream_refs, snapshot_path, deadline}` plus linked cancellation, never a Board object or lease token. The supervisor retains `renew`, and the existing heartbeat/expiry tasks remain active throughout peer processing. Recheck lease after hook completion and immediately before the ordinary fenced submission path. A hook must not publish a candidate itself. Parent-facing result contains only the final validated trace/hash, not unbounded intermediate chatter.

Build a separate immutable candidate snapshot from exact Git tree/blob identities. Do not casually mount the mutable author worktree and call it the candidate: ignored files and absent-file mount placeholders may differ from the committed tree. Git archive export-ignore/export-subst can also change extracted bytes, so use verified raw tree materialization or verify every path/blob/mode against the candidate. Each peer gets read-only `/workspace` and `/inputs` (spec, upstream, preceding-round trace), a fresh tmpfs, clean environment, no network, no credentials, no board DB or host Git metadata. The existing `run_bounded` supplies deadline/output limits/process-group cancellation; the read-only peer sandbox must expose **zero** owned writable mounts. Explicit peer argv is an operator input, never text synthesized by another worker.

Use fixed peer IDs and validated bounded JSON input/output, e.g. profile `argo.mesh.trace/1`, round number, candidate SHA, and findings with bounded IDs/messages plus path/blob-hash references. Host rejects extra fields, malformed output, mismatched candidate/round/peer identity, oversized arrays/strings, and missing participants. At most two rounds initially, bounded total trace size, and a global attempt deadline covering author plus peers. Within one round the host collects all three bounded results before permitting the next round. A failed/aborted required peer prevents a complete trace and submission; this is protocol completion, not a claim about application correctness. Independent completed peers' criticism is retained even when another peer disagrees. Do not replace the final trace with a synthetic unanimous verdict.

### Author revisions are a separate explicit choice

The smallest scope above reconciles reviews of one immutable candidate. If Mesh parity requires code revision after criticism, add one bounded author re-entry: the same leased author receives the round-one feedback read-only, alone edits owned paths, then the parent recaptures/commits a **new** candidate; all three final peers inspect that new SHA. The trace must preserve old/new candidate identities and show which findings were checked against which bytes. Never attach a round-one review of candidate A as approval of revised candidate B. This requires restructuring `_one`'s author/capture/commit phase into a bounded loop, not only adding a callback. The initial feature must not claim this revision loop until implemented and tested.

### Trace storage and Pantheon edge

Current `Board.put_artifact` accepts only owned logical paths, and submit requires their bytes to exist as regular files in the candidate. Therefore do **not** insert supervisor review traces through `put_artifact` under an unowned path, or modify the candidate after review to add the trace. For the smallest hook, return the bounded final trace with the dispatcher result and save an atomic immutable host-side trace under a per-ticket/per-epoch namespace; include its SHA256 and candidate identity in the result. Treat that sidecar as advisory evidence, not an accepted parent artifact. If durable Board attachment is required, add a distinct fenced supervisor evidence method/table with exact candidate/epoch binding and CAS integrity; do not overload artifact acceptance or reviewer approval.

The Pantheon edge should call this same trusted dispatcher protocol, not reimplement claims or run `runOpenItem` concurrently against the same Board ticket. Initially it can launch the finite explicit offline argv via `spawnPromise`, forward a linked signal, and parse a bounded final result/trace. Cancellation must reach the Python supervisor's SIGTERM handler and all descendants. Keep per-job roots/logs unique. The edge must not interpret its transport exit code, peers' opinions, or Pantheon `shipped` as ARGO acceptance. A fake/injected edge runner is sufficient to test the entire Mesh transport contract without installing provider clients or making calls.

Additional negative tests: three peers see one exact candidate; round two sees all round-one findings; peers cannot modify even owned author files; a forged/stale candidate/round response refuses; one hanging peer is terminated at deadline without orphaning siblings; missing peer prevents promised final trace; dissent survives reduction; result bytes remain bounded; author revision creates a new SHA and invalidates prior review bindings; three parallel author attempts cannot exceed the aggregate configured child ceiling; pre-submit trace completion cannot override lease loss, candidate policy failure, independent review, or either integration gate.

## Additive subclass seam assessment

The supervisor proposes only new files: `tools/mesh_dispatch.py`, `tools/test_mesh_dispatch.py`, `tools/MESH.md`, and a new Pantheon edge module/CLI/tests. Existing pinned dispatch/board files remain unchanged. This is viable for bounded concurrent authors plus read-only peer reconciliation:

* Subclass `Dispatcher`; override `run` for finite admission and `_one` only to establish/reset a `ContextVar` containing that attempt's row/stop/final trace. Install one author-runner wrapper at construction. It captures the existing `_one` stop event into its current context and forwards the original argv/environment/cwd/deadline/output arguments unchanged. Never mutate `self.runner`, `self.config`, or `self.current_row` per task. A ContextVar token must reset in `finally`, including cancellation, and missing context/stop at `_commit` must refuse.
* Override `_commit` to call `super()._commit`, then run the peer loop on an exact verified snapshot of the returned SHA, then return **that same** SHA. Existing heartbeat/expiry monitors remain active until `_one` finishes. Check the linked stop/deadline before/after every peer round and before returning. The existing `_one` does not immediately call `renew` after `_commit`; its next artifact publications are individually fenced by `Board.put_artifact`, and a `renew` precedes `Board.submit`. Preserve both. An optional additional heartbeat must not be mistaken for updating the original `_one` watchdog's monotonic deadline; only its existing renewal logic owns that local state.
* All peer tasks/children must settle before `_commit` returns or raises. Global supervisor cancellation must await per-attempt cleanup. In particular, canceling `_board('claim')` does not cancel its `to_thread` database operation: retain/shield the pending claim task and handle a late acquired row with fenced `fail_claim` before cleanup completes. Otherwise the new scheduler can exit with a lease it never recorded or watched. Test that exact race with a delayed fake/real claim seam.
* A subclass `_commit` hook does not support author revision after feedback because the superclass already captured `changes`, and later publishes artifacts from that capture. Running the author again there would make worktree, returned candidate and published artifact bytes disagree. Keep this version to peer reconciliation of the unchanged candidate; a future revision loop requires a separate reviewed lifecycle seam.
* Extend configuration only in the new module (immutable Mesh configuration wrapping/reusing `Config.validate`), and keep base defaults and the ordinary dispatcher behavior unchanged. Additive code does not automatically inherit a frozen policy endorsement: root's separate independent adoption of new control-plane files and named tests is still required. Test the new edge against an injected dispatcher process without invoking provider clients.

The simpler alternative is a new host supervisor that runs up to N existing one-ticket dispatch subprocesses, but that provides no exact pre-submit peer hook and makes stop/claim/trace coordination harder. The ContextVar + `_commit` subclass is therefore the narrower useful seam for this scope, provided its inherited lifecycle dependencies are explicitly covered by tests.
